# Plan d'action : services de saisie

> Feuille de route privée de la branche `feat/saisie` : l'objectif, le chemin, et où on en est.
> Légende : ✅ fait · 🔄 en cours · ⬜ à faire · ⏸️ reporté (autre branche)

**Dernière mise à jour :** 2026-09-24

## 🎯 Objectif

Le logiciel sait remplir lui-même tous les fichiers de saisie (tournoi, games, decks, oppos) : la future GUI n'aura plus qu'à
afficher un formulaire et appeler ces services, sans jamais éditer un fichier à la main.

```
  🖥️ GUI (plus tard)          ⚙️ services de saisie (cette branche)              📂 data/
┌──────────────────┐    ┌──────────────────────────────────────────┐    ┌──────────────────────────────┐
│ formulaire       │    │ tournoi   create / edit                  │    │ tournament.yaml              │
│ (champs remplis) │ ─> │ games     add / edit / delete            │ ─> │ games.csv                    │
│                  │    │ decks     create / version / statut …    │    │ decks/<deck>.yaml, _alias    │
│                  │    │ oppos     add_oppo                       │    │ oppos.yaml                   │
└──────────────────┘    └──────────────────────────────────────────┘    └──────────────────────────────┘
```

**Terminé quand :** chaque service est codé et testé (pytest), vérifie ses entrées avant d'écrire (tout ou rien),
et les fichiers qu'il produit sont relus sans erreur par `import`, `meta` et `stats`.

**Hors de cette branche** ⏸️ : l'interface graphique (`feat/gui`), y compris les services de **lecture** dont ses écrans auront besoin
(liste des tournois, des decks et versions, des oppos pour l'autocomplétion ; `load_deck_sheets` et `load_oppos` existent déjà) ;
pas de CLI complète (décision 2026-09-24).

## 🧰 Les services

Légende : 🟢 indispensable · 🟡 utile · ⚪ confort · ✅ existe déjà. Tous validés par l'utilisateur (2026-09-24) ; l'ordre suit la priorité.

### 🏆 Tournoi (`tournament.yaml`)

| Service | Rôle | |
|---|---|---|
| `create_tournament` | nouveau dossier copié depuis le modèle | 🟢 |
| `edit_tournament` | modifier la date, le lieu, la banlist, les notes | 🟡 |

### 🎮 Games (`games.csv`)

| Service | Rôle | |
|---|---|---|
| `add_games` | saisir une session (BO3 / BO1), avec les contrôles de l'import | 🟢 |
| `edit_game` | corriger une game : position, résultat, note (ex. L → W) | 🟢 |
| `edit_match` | corriger un BO entier : date, source, deck, version, oppo (toutes ses games) | 🟢 |
| `delete_game` | supprimer une game d'un BO | 🟡 |
| `delete_match` | supprimer un BO entier (par `match_id`) | 🟡 |
| `import_inbox` | les games saisies sur téléphone | ✅ |

Sans ces services, une erreur de saisie oblige à rouvrir `games.csv` à la main. Une game se désigne par son `match_id` et son numéro (`game`).

### 🃏 Decks (`decks/<deck>.yaml`)

| Service | Rôle | |
|---|---|---|
| `create_deck` | nouvelle fiche, avec la version v1 | 🟢 |
| `add_version` | nouvelle version (in / out / liste / notes) | 🟢 |
| `set_status` | `envisage` → `retenu` / `ecarte` | 🟢 |
| `edit_deck` | corriger le nom ou le commandant | ⚪ |
| `add_deck_alias` | appellations du deck (`_alias.yaml`) | ⚪ |

### ⚔️ Oppos (`data/oppos.yaml`)

| Service | Rôle | |
|---|---|---|
| `add_oppo` | nouvel oppo, ou nouvelle variante de nom | 🟡 |
| `import_meta` | ajoute les oppos du top 20 | ✅ |

Un oppo inconnu n'est pas bloquant (avertissement, la game est écrite avec le nom saisi, comme à l'import) : `add_oppo` sert à éviter
les noms en double dans les stats (*Ragavn* / *Ragavan*) ; la GUI pourra proposer « Ajouter *Ragavn* comme nouvel oppo, ou comme variante de *Ragavan* ? ».

### 📈 Déjà faits

`import_inbox`, `import_meta`, `generate_stats` (rapports et synthèse) ✅.

## 🧱 Les fichiers, couche par couche

Même architecture que le reste : chaque couche n'utilise que celles du dessous.

```
src/dcprepa/
├── __main__.py                ⬜ un module par service de saisie ; en-tête à corriger ▶️
├── services/
│   ├── games.py               ✅ add_games(), edit_game(), edit_match(),      🎮
│   │                             delete_game(), delete_match()
│   ├── oppos.py               ⬜ add_oppo()                                   ⚔️
│   ├── tournament.py          ⬜ create_tournament(), edit_tournament()       🏆
│   └── decks.py               ⬜ create_deck(), add_version(), set_status(),  🃏
│                                 edit_deck(), add_deck_alias()
├── domain/                    (règles pures, sans fichier)
│   ├── validation.py          🔁 validate_block() réutilisé tel quel          ✅
│   ├── games.py / rows.py     🔁 parse_bos(), build_rows() réutilisés         ✅
│   └── saisie.py              ⬜ contrôles nouveaux : slug, nom de deck, version 🧮
└── storage/                   (seul accès à data/)
    ├── games.py               🔁 append_rows() réutilisé ; ⬜ réécrire games.csv (.tmp) 📂
    ├── oppos.py               🔁 append_oppos() réutilisé                     ✅
    ├── tournament.py          ⬜ copier le modèle, écrire tournament.yaml     📂
    └── decks.py               ⬜ écrire une fiche, une version, un champ      📂

src/tests/                     ⬜ un fichier de tests par fichier de code    🧪
```

Réutilisation : l'import de l'inbox vérifie déjà un bloc (date, source, deck, version, oppo, games) et l'écrit dans `games.csv`.
`add_games()` reçoit **le même bloc** (un formulaire de la GUI = un bloc d'inbox) et passe par **les mêmes contrôles**.

## 🔎 Les étapes en détail

### ✅ 1. Décisions 🤔

Tranché par l'utilisateur (2026-09-24) :

- ✅ **Services retenus** : tous ceux des tableaux ci-dessus (🟢, 🟡 et ⚪).
- ✅ **Ordre** : par priorité, games d'abord (usage le plus fréquent).
- ✅ **Où écrire les games** : directement dans `games.csv`, avec les contrôles de l'import.
  L'inbox reste la saisie sur téléphone (GitHub), importée comme aujourd'hui.

```
 téléphone ──> inbox.yaml ──> import ──┐
                                       ├──> mêmes contrôles ──> games.csv
 GUI ──> formulaire ──> add_games() ───┘
```

- ✅ **Écriture des fiches deck** : modifier le texte du fichier (ajout en fin, remplacement d'une ligne `statut:`),
  comme `append_oppos`, pour garder les commentaires ; pas de réécriture complète par `yaml.dump`.
- ✅ **Slug d'un tournoi** : déduit du nom, pas demandé (« RelicFest 2026 » → `relicfest-2026`).
- ✅ **Corriger les games** : modifier une game ou un BO (ex. une game L → W), supprimer une game ou un BO.
- ✅ **Lancement minimal** : les services de saisie sont exposés dans `__main__.py`.

Détails validés par l'utilisateur (2026-09-24) :

- ✅ **Slug** : minuscules, accents retirés, tout caractère autre que lettre ou chiffre → `-` ; dossier déjà existant = erreur
  (pas de suffixe automatique `-2`, pour ne pas créer un doublon sans le voir).
- ✅ **Champs d'un tournoi** : `name` obligatoire ; `date`, `location` facultatifs ; `format` = `Duel Commander` par défaut ;
  `banlist` et `notes` via `edit_tournament`.
- ✅ **Modifier une game** : `edit_game` change position, résultat, note ; `edit_match` change date, source, deck, version, oppo
  pour toutes les games du BO, avec les contrôles de l'import. Date changée → nouveau `match_id` (prochain numéro libre de la nouvelle date).
- ✅ **Supprimer une game** : les games suivantes du BO sont renumérotées (3 → 2) ; un BO3 réduit à une game devient un BO1 → avertissement.
- ✅ **Exposer les services** : arguments en ligne de commande avec `argparse` (bibliothèque standard, aucune dépendance),
  un module par service, sans questions interactives, ex. `python -m dcprepa tournoi-creer "RelicFest 2026" --date 31/10/2026`.
  Remplace la lecture actuelle de `sys.argv` ; les modules existants (`import`, `meta`, `stats`) gardent la même commande.
- ✅ **Qui code** : Claude code et explique chaque étape (quoi, à quoi ça sert) ; l'utilisateur supervise et valide avant la suivante.
