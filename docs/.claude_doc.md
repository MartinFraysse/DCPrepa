## 01 · Présentation

### Contexte et objectifs — `01-presentation/index.md`
<!-- Ce que fait le projet, pour qui, pourquoi. Périmètre et non-objectifs. -->
- But : préparer un gros tournoi de Duel Commander (Magic: The Gathering).
- À terme, le logiciel (et sa GUI) permettra de remplir tous les fichiers de saisie (tournoi, decks, alias, oppos, inbox) ; ils restent modifiables à la main.
- Besoin : un environnement pour suivre les entraînements, faire des statistiques sur le méta et tester différents decks.
- Outil **générique**, réutilisable pour d'autres tournois (pas lié à une date).
- Sources de games : paper entre amis, MTGO, Cockatrice en self-play (deux decks joués par l'utilisateur).
- Données minimales par game : deck utilisé, deck adverse (« oppo »), play/draw (OTP / OTD), résultat, note/ressenti (texte libre, pas de note chiffrée).
- Plusieurs BO d'une même session (ex. 3 BO3, ou 2 BO3 + 1 BO1) doivent se saisir facilement.
- Format : surtout des BO3, parfois des games seules (BO1).
- Méta : données MTGTop8 importées + données perso ; l'adversaire est décrit uniquement par son deck (= son commandant), ni nom de joueur ni archétype.
- Suivi des versions des decks (évolution des listes) et comparaison des résultats par version.
- Consultation souhaitée à la fois sur GitHub (lisible dans le dépôt) et via un logiciel local facile à récupérer depuis GitHub.
- Forme de l'outil : pas encore décidée.

### Glossaire — `01-presentation/glossaire.md`
<!-- Termes propres au projet : terme → définition courte. -->
- Duel Commander (DC) → format 1v1 de Magic : deck singleton de 100 cartes mené par un commandant, 20 points de vie.
- Deck = commandant → en DC un deck est identifié par son commandant.
- Pas de sideboard en Duel Commander → aucun champ side dans les fiches deck.
- Oppo → le deck adverse (son commandant).
- Méta → ensemble des decks (archétypes) joués et leur fréquence dans le format.
- OTP / OTD → *on the play* (on commence) / *on the draw* (l'adversaire commence).
- Game → une manche, à la fin de laquelle un joueur gagne.
- BO1 / BO3 → une seule game / best of 3 games : jusqu'à 3 games, gagné à 2 victoires.
- MTGTop8 → site de résultats de tournois (decks classés), source des données de méta.

## 03 · Architecture

### Vue d'ensemble — `03-architecture/index.md`
<!-- Composants, flux entre eux, arborescence utile. -->
- Import : `services/import_inbox.py::import_inbox(tournament_dir, oppos_path)` → `ImportReport` (dataclass : blocks, matches, games, errors, warnings, `ok`).
  Lit tout (inbox, decks, oppos, match_id) ; erreur de lecture ou inbox vide → arrêt sans écriture ; valide tous les blocs ;
  la moindre erreur → rien n'est écrit ; sinon `append_rows` puis `clear_inbox`. Les erreurs d'écriture (OSError) remontent à l'interface.
- Contrôle d'un bloc de games partagé : `domain/blocks.py::prepare_block` (deck ramené à son fichier, `validate_block`, oppo normalisé
  ou self-play, `build_rows`) ; références lues par `services/games.py::load_game_references`. Utilisé par l'import et par la saisie.
- Saisie : `services/games.py::add_games(tournament_dir, block, oppos_path)` → `GamesReport` (matches, games, match_ids, errors, warnings) ;
  un bloc = un formulaire de la GUI, mêmes champs et messages que l'inbox ; tout ou rien ; oppo inconnu = avertissement.
- Corrections : `edit_game` (position, résultat, note), `edit_match` (date, source, deck, version, oppo), `delete_game`, `delete_match`
  (`services/games.py`, calcul dans `domain/edits.py`). Le BO corrigé est reconstruit en bloc et revérifié par `prepare_block` ;
  notes par game gardées ; `match_id` changé seulement si la date change ; `games.csv` réécrit entier (`write_games`, `.tmp`).
  Une game se désigne par `match_id` + numéro ; game supprimée → renumérotation ; BO3 réduit à 1 game → avertissement (BO1).
- Oppos : `services/oppos.py::add_oppo(oppos_path, name, variant_of=None)` : nouvel oppo à la fin de `data/oppos.yaml`
  (commentaire « Ajouté par la saisie le … »), ou variante insérée sous sa référence (`insert_variant`, texte relu avant écriture).
  Un oppo inconnu n'est jamais bloquant (avertissement) : `add_oppo` évite les noms en double dans les stats.
- Tournoi : `services/tournament.py::create_tournament(data_dir, name, fields)` : slug déduit du nom (`slugify` : minuscules, sans accents,
  autres caractères → `-`) ; dossier existant = erreur ; copie via `<slug>.tmp` renommé ; README et `stats/_modele-deck.md` retirés.
  `edit_tournament(tournament_dir, changes)` : name, format, date, location, banlist, notes (slug fixe).
- Écriture d'un champ YAML sans perdre les commentaires : `storage/yaml_text.py::set_fields` (commentaire de fin de ligne gardé et aligné,
  champ absent ajouté à la fin, texte relu avant écriture).
- Code Python dans `src/dcprepa/`, découpé en couches (un dossier par rôle) :
  `interfaces/` (GUI ; seule couche qui affiche) → `services/` (cas d'usage : import de l'inbox, saisie, méta, génération des stats)
  → `domain/` (règles métier pures, sans fichier ni affichage) et `storage/` (seul accès à `data/`).
- Une couche n'importe que celles du dessous ; `domain/` et `services/` renvoient des données ou lèvent une erreur, jamais de `print` ni `sys.exit`.
- Tests dans `src/tests/`, même arborescence que `dcprepa/`.

### Décisions — `03-architecture/decisions/`
<!-- Un choix par puce : décision → raison. Chacune deviendra une fiche ADR. -->
- Architecture en couches (domain / storage / services / interfaces) → une GUI est prévue : elle réutilisera services et domain sans rien dupliquer.
- Données en fichiers texte versionnés (CSV pour les games, YAML pour les decks) → lisibles sur GitHub, historique porté par git.
- Un dossier par tournoi préparé (1er : RelicFest 2026) → outil générique, réutilisable d'un tournoi à l'autre.
- Decks et leurs versions rangés **dans le dossier du tournoi** → les listes sont modifiées pendant la préparation de chaque tournoi.
- CLI reportée à plus tard ; on commence par le format des données.
- Adversaire réduit à « oppo » (son deck) : pas de nom de joueur ni d'archétype → garder l'essentiel.
- Ressenti chiffré retiré ; un seul champ texte `note/ressenti` → garder l'essentiel.
- Inbox : un bloc par session, BO séparés par `/` dans `games` → saisir plusieurs BO d'un coup sur téléphone.

## 04 · Référence

### Configuration — `04-reference/configuration.md`
<!-- Fichiers de config, variables d'environnement, valeurs par défaut. -->
- Format des dates (choix de l'utilisateur) : `JJ/MM/AAAA` partout où une date est saisie ou lue (`tournament.yaml`, `inbox.yaml`, colonne `date` de `games.csv`).
  PyYAML les lit comme des chaînes : les convertir à l'import (`datetime.strptime(d, "%d/%m/%Y")`) et trier sur la date convertie, jamais sur la chaîne.
  `match_id` aussi en `JJ/MM/AAAA-NN` (demande de l'utilisateur). Seule exception : les dossiers de `meta/` restent `AAAA-MM-JJ/` (`/` interdit dans un nom, et tri par date naturel).
- Modèle de tournoi : `data/templates/tournament/`, copié à la main (`cp -r data/templates/tournament data/tournaments/<slug>`), mode d'emploi dans son `README.md`.
  Contient les fichiers vides/commentés et `decks/_modele.yaml` (fiche deck vierge). L'import devra ignorer `data/templates/` et les fichiers `decks/_*.yaml`.
- Dossier d'un tournoi : `data/tournaments/<slug>/` (slug en minuscules, ex. `relicfest-2026`).
  - `tournament.yaml` : name, slug, format, date, location, banlist, notes. Pas de liste des decks : le dossier `decks/` et le `statut` de chaque fiche suffisent.
  - `games.csv` : une ligne par game ; colonnes `date,match_id,game,source,deck,version,oppo,position,resultat,note/ressenti`.
    `position` = OTP/OTD, `resultat` = W/L (une game n'est jamais nulle ; seul un BO3 peut l'être, à 1-1), `match_id` regroupe les games d'un BO3.
  - `inbox.yaml` : saisie mobile, YAML multi-documents sans indentation, un bloc par **session** (même date, source, deck, version, oppo) séparé par `---`.
    Champs : date, source (paper|mtgo|cockatrice), deck, version, oppo, games, note/ressenti.
    `games` : BO séparés par `/`, games d'un BO séparées par `,` (OTP/OTD + W/L), ex. « OTP W, OTD W / OTD L, OTP W, OTD L / OTP W » = 2 BO3 + 1 BO1.
    À l'import : un `match_id` par segment entre `/`, une ligne de `games.csv` par game. Lu avec `yaml.safe_load_all` ; un `---` final produit un document `None` à ignorer.
  - `decks/<deck>.yaml` : name, commandant (nom exact de la carte, face avant), statut (envisage | retenu | ecarte, sans accents), versions (liste ordonnée).
    Chaque version : version (v1, v2…), liste (bloc `|`, lignes « 1 Nom de carte », export MTGO/Moxfield ; obligatoire en v1),
    in / out (listes de cartes, diff avec la version précédente), notes. Pas de date (jugée non pertinente). Le nom du fichier = identifiant `deck` de l'inbox.
    Un `#` à l'intérieur du bloc `liste: |` n'est pas un commentaire : il ferait partie de la liste.
    Indentation du bloc libre (détectée sur la 1re ligne) mais identique pour toutes les lignes ; « Summon: Yojimbo » y est sans risque.
  - `decks/_alias.yaml` (par tournoi, facultatif, ignoré par `load_decks` car commence par `_`) : nom du fichier deck → variantes.
    Un deck saisi est reconnu par le nom de son fichier, le `name:` de sa fiche ou une variante (comparaison souple) et ramené au nom du fichier
    (`storage/decks.py::load_deck_aliases`, `domain/names.py::build_name_index`, `domain/decks.py::resolve_deck`).
    Inconnu → erreur bloquante avec la liste des decks disponibles. Self-play `deck@version` : son deck est résolu pareil ; inconnu → avertissement.
    Erreurs bloquantes : `_alias.yaml` cite un deck sans fiche, variantes pas en liste, même appellation pour deux decks.
  - `data/oppos.yaml` (hors tournoi, commun à tous) : mapping nom de référence (nom court, `/` pour les partenaires) → liste de variantes ; l'import normalise `oppo` avec. Vide → `None` au chargement.
    Complété automatiquement par `meta` : oppos du top 20 absents ajoutés à la fin (commentaire daté, nom court + variante complète) via `storage/oppos.py::append_oppos`.
  - `oppo` en self-play Cockatrice : `<deck>@<version>` (un de ses propres decks).
  - `match_id` : généré à l'import, `JJ/MM/AAAA-NN` (ex. `02/10/2026-01`) ; NN repart de 01 chaque jour et suit le plus grand NN existant ce jour-là
    (`games.csv` + blocs précédents du même import), sans combler les trous (`domain/rows.py::next_match_id`).
    La date (colonne `date` et préfixe du `match_id`) est réécrite avec ses zéros : `2/10/2026` → `02/10/2026` (`normalize_date`).
  - Conversion bloc → lignes : `domain/rows.py::build_rows` (une ligne par game, un match_id par BO, source en minuscules,
    note recopiée sur chaque ligne du bloc, espaces multiples réduits).
  - `storage/games.py` : `read_match_ids` (vérifie l'en-tête exact, tolère BOM et CRLF) et `append_rows`
    (module `csv`, guillemets automatiques, fins de ligne conservées, écriture via `.tmp`).
  - `meta/` (dans le tournoi, car le méta change d'un tournoi à l'autre) : un dossier par import MTGTop8, `AAAA-MM-JJ/`, avec `general.csv` (Last 2 Months)
    et `paper.csv` (Paper Last 2 Months) ; imports précédents gardés ; colonnes `oppo,decks,poids` (nom de référence, listes estimées, part du méta en %, 2 décimales) ; top 20 de chaque méta.
    Période couverte choisie à l'import ; les stats utilisent le fichier le plus récent. Top 10 du méta = 10 plus gros `poids`.
  - `stats/` : rapports Markdown générés, jamais édités à la main.
- Import **tout ou rien** (règle de l'utilisateur, prioritaire) : si un seul bloc de l'inbox est invalide, rien n'est importé,
  `games.csv` et `inbox.yaml` ne sont pas modifiés, et toutes les erreurs de tous les blocs sont affichées.
  Tout est validé avant la moindre écriture ; si tout est valide, les lignes sont ajoutées à `games.csv` puis l'inbox est vidée (en-tête gardé).
  Lecture : `storage/inbox.py::read_inbox(path)` découpe le texte sur les lignes `---` (ligne seule, espaces tolérés) et lit chaque bloc avec `yaml.safe_load`,
  pour signaler toutes les erreurs de syntaxe d'un coup (« bloc 2 : YAML illisible ligne 5 : … », message PyYAML en anglais) ; `safe_load_all` s'arrêterait à la première.
  Vidage : `clear_inbox(path)` garde les lignes vides/commentaires du début (jusqu'à la 1re ligne utile ou `---`), conserve LF/CRLF,
  écrit dans `inbox.yaml.tmp` puis le renomme par-dessus (`Path.replace`) : l'inbox est soit intacte, soit vidée, jamais à moitié.
- Erreurs de validation d'un bloc
  (deck sans fiche dans `decks/`, version absente de la fiche, source hors `paper|mtgo|cockatrice`, date mal formée).
  Un `oppo` absent de `data/oppos.yaml` est gardé tel quel, avec un **avertissement** (n'empêche pas l'import, décision de l'utilisateur).
  Normalisation : `storage/oppos.py::load_oppos` lit le fichier ; `domain/oppos.py::build_oppo_index` (via `domain/names.py`, partagé avec les decks) construit « forme souple → référence »
  (minuscules, espaces en trop retirés ; une forme vers deux références = erreur) ; `normalize_oppo` renvoie (référence, avertissement|None) ;
  self-play `deck@version` gardé tel quel.
  Code : `domain/validation.py::validate_block(block, decks)` ; `decks` = {nom: [versions]} construit par `storage/decks.py::load_decks(tournament_dir)`
  (lit `decks/*.yaml` hors `_*`, nom = nom du fichier ; fiche illisible, sans versions, version sans identifiant ou en double → écartée et signalée, les autres chargées) ; renvoie la liste des erreurs ([] = valide).
  `date: 2026-10-02` (ISO) est lu par PyYAML comme un objet date → refusé avec le message de format ; `version: 1.10` devient `1.1`.
- Pièges YAML de l'inbox, à gérer à l'import : une valeur contenant « : » ou commençant par « # » casse ou tronque la ligne ;
  `version: 3` est lu comme entier et `1.10` comme flottant `1.1` → convertir en texte / conseiller le préfixe `v`.

### Statistiques — `04-reference/statistiques.md`
<!-- Stats calculées par le logiciel, définitions et règles d'affichage. -->
- Rapports par deck (Markdown dans `stats/` du tournoi), calculés depuis `games.csv`, `decks/`, `meta/` et `data/oppos.yaml`.
- Self-play (oppo = `deck@version`) : exclu du winrate général et des autres stats, affiché dans une section à part du rapport deck.
- Winrate général du deck : toutes versions confondues, en réunissant toutes les games (victoires / games jouées).
- Winrate par oppo (matchup), OTP / OTD, par source (paper, cockatrice, mtgo), par BO3 en plus de par game.
- Matchup croisé avec OTP / OTD, affiché seulement pour les oppos avec assez de games.
- Poids de chaque oppo dans le méta papier et général (dernier dossier daté de `meta/`).
- Winrate attendu au tournoi = Σ (poids × winrate du deck contre l'oppo) / Σ poids, sur les seuls oppos du méta (top 20) joués dans la base choisie :
  le reste du méta est ignoré. 4 valeurs : méta papier / général × par game / par BO3 (un oppo joué seulement en BO1 ne compte pas en BO3).
  Affiché `49.8 % (16.2 % du méta)` : couverture = Σ poids retenus ; ⚠️ sous 30 % ; `—` si aucun oppo du méta joué.
  Code : `domain/synthese.py` (`expected_winrate`, `ExpectedWinrate`). Les noms MTGTop8 du top 20 sont ajoutés automatiquement à `data/oppos.yaml` par `meta`.
- Section Général du rapport de deck : tableau `| | Par game | Par BO3 |`, lignes Winrate, Winrate attendu (méta papier), Winrate attendu (méta général).
- Matchups non testés : oppo dans le top 10 du méta papier (poids ↓, puis nom) ET moins de 10 BO3 ET moins de 30 games contre lui,
  pour les decks `retenu` / `envisage` seulement. Atteindre 10 BO3 ou 30 games suffit (les BO1 comptent via les games).
  Code : `domain/synthese.py::untested_matchups`.
- `synthese.md` (`domain/synthese_report.py::render_synthese`) : Decks (tous, tri statut retenu → envisage → ecarte → inconnu, puis attendu papier games ↓ ;
  colonnes winrates + attendu papier games / BO3), Méta (union des top 20 papier et général, tri poids papier ; une colonne par deck retenu / envisagé, winrate par game),
  Matchups non testés (Deck, Oppo, Rang papier, Poids papier, BO3 joués, Games jouées).
- `stats` écrit `synthese.md` en plus des rapports de deck (tout ou rien) ; titre = `name` de `tournament.yaml` (sinon nom du dossier, `storage/tournament.py`) ;
  avertissement si le statut d'une fiche est vide ou inconnu ; fiche nommée `synthese` ou `README` (majuscules comprises) = erreur bloquante.
- Taille d'échantillon : nombre de games à côté de chaque winrate ; signaler ceux qui reposent sur moins d'une dizaine de games.
- Fichiers dans `stats/` : `README.md` (conventions), `synthese.md` (decks côte à côte, méta, winrate attendu, matchups non testés), `<deck>.md` (détail : général, versions, position, source, matchups).
  Tant que la commande `stats` n'existe pas, ce sont des rapports-modèles remplis de `—` : ils fixent la sortie attendue du logiciel. Modèle : `data/templates/tournament/stats/_modele-deck.md`.
- BO3 = BO de 2 ou 3 games ; BO d'une seule game = BO1 : compte dans les winrates par game, pas dans « Par BO3 ».
- Tant que le méta n'existe pas : matchups triés par nombre de games (décroissant), « Poids papier », « Poids général » et winrates attendus à `—`.
- Un rapport `stats/<deck>.md` par fiche deck, même sans aucune game (rempli de `—`).
- `_modele-deck.md` n'est jamais modifié : c'est la spec du rapport ; le logiciel écrit `stats/<deck>.md` en suivant sa structure.
- Format d'affichage : `55 % (66/120)` = victoires / games ; BO3 nul (1-1) = BO3 non gagné ; ⚠️ sous 10 games ; `—` = pas de donnée.
- Pourcentage au dixième, décimale nulle omise (`55 %`, `12.2 %`, `66.7 %`) ; seuil ⚠️ appliqué au total affiché (games, ou BO3). Code : `domain/winrate.py` (`Winrate`, `format_percent`).
- Deux winrates distincts partout où c'est possible : par game (toutes les games) et par BO3 (2-3 games) ; Position reste par game seulement.
- Matchups : colonnes « Meilleure version (games) » et « Meilleure version BO3 » = version au meilleur winrate contre l'oppo + écart au winrate du matchup (`v2 (+12)`) ; ⚠️ sous 10 games / BO3 de cette version ; `—` si une seule version a joué l'oppo ; égalité → plus de games, puis plus récente (`domain/stats.py::best_version`).
- Méta : les stats lisent le dossier `meta/AAAA-MM-JJ/` le plus récent (`storage/meta.py::load_latest_meta`, `general.csv` + `paper.csv` requis). Présent → colonnes « Poids papier » et « Poids général », tri papier ↓, puis absents du papier par général ↓, puis games ; absent → tri par games. Fichier manquant ou invalide = erreur bloquante ; ancien `meta/AAAA-MM-JJ.csv` ignoré.
- Par version : winrate (games et BO3) affiché, plus un indicateur d'écart =
  winrate de la version − moyenne simple des winrates des autres versions (chacune pèse autant, quel que soit son nombre de games),
  en points (ex. v1 à 53 %, v3 à 55 % → moyenne 54 % ; v2 à 57 % → v2 : +3).
  Pas d'indicateur si le deck n'a qu'une version.
